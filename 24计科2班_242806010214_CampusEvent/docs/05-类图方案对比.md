# 类图方案对比：名额检查放公共流程 vs 放策略

> 版本：v1.1 ｜ 日期：2026-11-22 ｜ 对应需求基线 v1.3 ｜ 选定：方案甲（2026-11-22）｜ 用途：类图 v1.0 与报告“设计取舍”素材
> 说明：两套都能自圆其说，差别只在“名额检查这个不变量放在哪”。下列“文件数”按职责分离的参考结构估算；实际可合并文件，但耦合关系与改动面结论不变。

> 选定结果：方案甲。Q-07 由 C 修正为 A；类图 v1.0 与类模型 v1.0 已按甲绘制。

## 0. 共同部分（两套都有，12 个类/接口）

| 类 / 接口 | 类型 | 一句话职责 |
|---|---|---|
| Student | 实体 | 学生身份与姓名，报名人的唯一标识。 |
| Activity | 实体 | 活动信息（名称、类型、时间、地点、容量、报名方式）。 |
| Registration | 实体 | 一次报名的记录与状态（待审核/已通过/已拒绝/已取消）。 |
| Message | 实体 | 站内通知记录（学生、活动、内容、已读）。 |
| RegistrationRepository | 接口 | 报名的持久化与按活动统计“已通过”数量。 |
| RegistrationService | 服务 | 编排报名、审批、取消用例；控制事务与事件发布。 |
| RegistrationPolicy | 接口 | 报名策略契约：决定一次报名的结果。 |
| DirectRegistrationPolicy | 策略实现 | 直接报名规则：报名即通过。 |
| AuditRegistrationPolicy | 策略实现 | 审核规则：提交后待审核，审批后通过或拒绝。 |
| RegistrationEventPublisher | 事件发布者 | 维护观察者列表，发布报名/审批事件（Subject）。 |
| RegistrationObserver | 接口 | 观察者契约：接收报名/审批事件。 |
| MessageObserver | 观察者实现 | 把事件写成站内消息（未来可加邮件等第二渠道）。 |

共同关联/依赖：
- Registration 关联 Student（多对一）与 Activity（多对一）；Message 关联 Student 与 Activity。
- RegistrationService 依赖 RegistrationPolicy、RegistrationRepository、RegistrationEventPublisher。
- DirectRegistrationPolicy、AuditRegistrationPolicy 实现 RegistrationPolicy。
- RegistrationEventPublisher 对 RegistrationObserver 为一对多；MessageObserver 实现 RegistrationObserver，并创建 Message。
- 持久化实现（SQLite Repository）不展开，只保留接口。

## 1. 方案甲：名额检查放公共流程

### 1.1 类
在共同部分之外，**新增 1 个类**：
- **CapacityChecker**（领域服务）：统一名额检查——统计活动“已通过”数、计算剩余名额，并在提交/审批时决定是否放行。

共 13 个类/接口。

### 1.2 依赖箭头（新增/变化部分）
- RegistrationService → CapacityChecker（提交与审批前调用）
- CapacityChecker → RegistrationRepository（取已通过数）
- RegistrationService → RegistrationPolicy（仍然依赖抽象）
- 策略内部**不依赖** CapacityChecker，也不判名额。

### 1.3 流程
- 提交：Service 做公共校验（活动未开始、无重复报名）→ 取策略 → policy.decide() 返回“已通过/待审核” → 若“已通过”，CapacityChecker.ensure() 检查名额 → 创建报名 → 发布事件。
- 审批：Service 校验待审核 → CapacityChecker.ensure() → 状态改为已通过/已拒绝 → 发布事件。

### 1.4 加第三种报名规则（如候补）
- 新增 1 个策略文件（policies/third.py）
- 修改 1 个注册表文件（policies/registry.py）
- 新增 1 个测试文件
- **最小 3 个文件**。若新规则引入新状态（如 WAITLISTED）或新时机（截止后抽签/候补提升），还要改模型状态枚举与 RegistrationService，约 **5–6 个文件**；但名额检查逻辑不用复制。
- 若只是调整名额口径（例如“待审核也预占名额”）：**只改 CapacityChecker 1 个文件**（加测试），策略不动。

### 1.5 优点与代价
优点：
- 名额是跨规则的公共不变量，集中一处，C4/C8 的“不超卖”更容易证明。
- 策略接口保持简单（只决定结果），没有 submit/approve 双阶段方法。
- 名额口径变化只改一处，测试集中。

代价：
- 策略变“薄”，可能被质疑只是状态选择器。
- Service 流程隐含假设“立即通过=占名额、待审核=不占”；新规则若改变这个假设，Service 要改。
- 策略无法独立表达“满员转候补”等规则特有行为，需要 Service 配合。

## 2. 方案乙：名额检查放进各自策略

### 2.1 类
共同部分之外**不新增类**（名额逻辑进策略内部）。
共 12 个类/接口。

### 2.2 依赖箭头（变化部分）
- RegistrationService → RegistrationPolicy（仍依赖抽象）
- DirectRegistrationPolicy → RegistrationRepository（自查已通过数并判名额）
- AuditRegistrationPolicy → RegistrationRepository（审批时自查名额）
- **没有 CapacityChecker**。
- 策略接口需要同时覆盖“提交”和“审批”两个时机（例如 policy.submit() 与 policy.approve()），DirectPolicy 的 approve 实际用不到。

### 2.3 流程
- 提交：Service 做公共校验 → 取策略 → policy.submit()；DirectPolicy 内部判名额并返回已通过，AuditPolicy 直接返回待审核 → 创建报名 → 发布事件。
- 审批：Service 校验待审核 → policy.approve()；AuditPolicy 内部判名额 → 更新状态 → 发布事件。

### 2.4 加第三种报名规则（如候补）
- 新增 1 个策略文件（内含自己的名额检查，逻辑从现有策略复制）
- 修改 1 个注册表文件
- 新增 1 个测试文件
- **最小 3 个文件**；若新规则需要接口新增方法，还要改策略接口文件 + 现有 2 个策略（未来 3 个），约 **5–6 个文件**。
- 若调整名额口径：要改 Direct、Audit 两个现有策略（未来 3 个），是 **2–3 个文件**，且容易改漏。

### 2.5 优点与代价
优点：
- 每条规则自包含，Service 只做编排，规则扩展时 Service 基本不动。
- 新规则的名额语义可以不同（如候补规则允许超额排队），不需要服务加分支。
- 对“规则间差异大”的系统更自然。

代价：
- 名额检查重复实现，规则越多重复越多；改口径要逐个策略改，存在不一致风险。
- 策略接口承担提交/审批两阶段，DirectPolicy 的 approve 是空实现或抛异常，接口不够干净。
- Service 没有兜底；某策略漏判名额就直接超卖。
- 每个策略的测试都要重复准备容量数据。

## 3. 对比表

| 维度 | 方案甲（公共 CapacityChecker） | 方案乙（策略内检查） |
|---|---|---|
| 类数量 | 13 | 12 |
| 名额逻辑位置 | Service/CapacityChecker 一处 | Direct、Audit 各一份 |
| 修改名额口径 | 1 个文件 | 2–3 个文件（随规则增长） |
| 加第三种规则 | 3 个文件起，特殊时机 5–6 | 3 个文件起，接口扩展 5–6 |
| 策略接口复杂度 | 低（单一结果） | 高（submit/approve 两阶段） |
| 不超卖保证 | 集中、易证明 | 依赖每个策略自觉 |
| 测试重复度 | 低 | 高 |
| Service 复杂度 | 较高（含名额分支） | 低（纯编排） |
| 规则差异大时 | 较差 | 较好 |
| 与 Q-07 的关系 | 接近 A（公共规则） | 接近 B（策略责任） |

## 4. 推荐：方案甲，但先说甲的毛病

甲的毛病：
1. **策略变薄**：RegistrationPolicy 只返回“已通过/待审核”，容易被评审问“这还算策略模式吗”。答辩时要能说清：变化点是“报名通过方式”，名额是跨规则的公共不变量，故不放进策略。
2. **Service 流程有隐式假设**：代码里会有“如果策略返回已通过，就检查名额”的分支；第三种规则若是候补/抽签/分时段，这个假设不成立，Service 要改，OCP 在流程层被破坏。
3. **策略无法单独表达名额相关变体**：比如“满员自动转候补”“按课程配额”，甲需要 Service 支持新分支，不是加一个策略文件就完事。
4. **与 Q-07 不一致**：你之前定的是 C（服务前置 + 策略兜底）；甲实际是 A，需要改决策记录，否则报告自相矛盾。
5. **CapacityChecker 可能成为热点**：所有提交/审批都依赖它，未来若把多种配额规则塞进去，会膨胀成“小上帝类”。

为什么仍推荐甲：
- 名额是 B.2-3 定义的**全局不变量**，集中一处最不容易超卖，C4/C8 的验收最稳。
- 两套规则在“名额”上没有差异（直接型提交时查、审核型审批时查），差异只在“结果状态”，所以把差异放策略、把共性放公共流程，划分更干净。
- 策略接口简单，测试集中，课程项目两周内更可控。
- 报告里可以写“甲把不变量集中、乙把变化点下放；本项目规则差异集中在审批方式而非名额语义，故选甲”。

乙什么时候更值得选：
- 如果 CR 的第三种规则在**名额语义或时机**上明显不同（候补、抽签、分时段），乙的“规则自包含”更稳，Service 不用长分支；代价是名额逻辑重复，需要在报告里承认。

- 方案乙 ≈ Q-07 的 B（策略责任）。
