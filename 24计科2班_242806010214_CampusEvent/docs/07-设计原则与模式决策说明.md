# 实验二 设计原则与设计模式决策说明

> 版本：v1.1 ｜ 日期：2026-11-22 ｜ 项目：CampusEvent（24计科2班_242806010214）
> 对应材料：需求基线 v1.3、用例图/用例说明 v1.1、类图/类模型 v1.2、时序图/时序模型 v1.2（含取消 v1.0）
> 依据：实验指导书 3.3 设计任务 A–D、3.6、3.8；知识库《UML图速查》2.1、《面向对象分析与设计》2.4、《设计模式》2.5.6 与 2.5.9

## 1. 设计目标与约束

- 支持“直接报名”和“管理员审核”两类报名规则，且能扩展到第三种规则。
- 报名结果通过站内消息通知，通知失败不得让合法报名静默消失。
- 数据持久化，状态转换符合 B.2-1～B.2-7；容量不得超卖。
- 设计要能被评审、被测试、被变更；不引入消息队列等超出范围的设施。
- 本说明回答三个问题：职责怎么分、为什么用这两个模式、名额检查为什么放在公共服务里。

## 2. 职责划分（3.3-A）

| 类 / 接口 | 职责 | 变化原因（单一职责） |
|---|---|---|
| Student / Activity / Registration / Message | 领域实体，承载数据与少量自身判断 | 字段或业务属性变化 |
| StudentRepository / ActivityRepository / RegistrationRepository | 持久化与查询契约 | 存储实现或查询方式变化 |
| ActivityService | 编排活动创建/编辑/软删除/浏览（UC-01/02） | 活动管理流程变化 |
| RegistrationService | 编排报名/审批/取消，控制事务与事件发布 | 报名流程变化 |
| MessageService | 编排消息列表与已读（UC-06） | 消息查看流程变化 |
| PolicyProvider / PolicyRegistry | 按 policy_type 提供策略；Registry 是具体实现 | 策略注册/查找方式变化 |
| RegistrationPolicy | 报名策略契约 | 规则契约变化 |
| DirectRegistrationPolicy / AuditRegistrationPolicy | 两类报名规则 | 各自规则变化 |
| CapacityChecker | 公共名额规则 | 名额口径/容量规则变化 |
| RegistrationEvent | 事件数据载体 | 事件字段变化 |
| RegistrationEventPublisher | 维护观察者、发布事件 | 分发机制变化 |
| MessageRepository | 消息持久化与查询 | 存储/查询方式变化 |
| RegistrationObserver / MessageObserver | 通知扩展点 / 经 Repository 写站内消息 | 通知渠道变化 |

依赖方向（详见类图 v1.2）：
- RegistrationService 依赖抽象（Repository、Policy、Observer、Publisher），不依赖具体策略或 SQLite 实现。
- 策略实现只依赖 RegistrationPolicy 契约，**不依赖 CapacityChecker**（方案甲的关键检查点）。
- CapacityChecker 依赖 RegistrationRepository 统计已通过数。
- MessageObserver 依赖 RegistrationObserver 契约、Message 与 MessageRepository，不依赖 Service。
- StudentRepository 只有 find_by_id，保留原因：让 Service 依赖抽象、测试可替换；若评审认为接口过薄，可合并到 Student 服务，但会增加耦合。

## 3. 模式一：策略模式（3.3-B）

### 3.1 结构与参与者

- 抽象：RegistrationPolicy，操作 decide(activity): RegistrationStatus。
- 具体策略：DirectRegistrationPolicy 返回 APPROVED；AuditRegistrationPolicy 返回 PENDING。
- 上下文：RegistrationService；通过 PolicyProvider（PolicyRegistry 实现）按 activity.policy_type 取策略。
- 客户：Student（间接）、Admin（审批不属于策略选择）。

### 3.2 协作

报名时序图 v1.2：Service 取策略 → policy.decide(activity, student) → 只根据返回状态决定是否走名额检查（APPROVED 走 ensure_available，PENDING 直接保存）；重复报名在进入策略前用 alt 拒绝。Service 不判断具体策略类，也没有大量 if activity.type 分支。

### 3.3 为什么用策略模式

- 变化点是“报名通过方式”，不是“名额规则”；直接型与审核型在结果状态上不同，适合用稳定接口封装。
- 满足开闭原则：新增规则主要是新增策略实现 + 注册，不改 Service 的策略选择逻辑。
- 便于测试：每个策略可独立测试，不依赖数据库；Service 可用假策略测试编排。

### 3.4 名额检查归属论证（Q-07 = A，甲方案）

- 名额是 B.2-3 定义的**跨规则公共不变量**：只统计已通过、待审核不占、满员不得再批。它不是某条规则独有的算法。
- 放在 CapacityChecker 的理由：
  1. 一处实现，C4/C8 的“不超卖”容易证明；
  2. 改名额口径只改一个类，不会出现两条策略各写一份、改漏一份；
  3. 策略保持纯粹：只回答“通过方式”，不重复实现公共规则。
- 不放在策略里的理由：两条规则的名额语义相同（直接型提交时查、审核型审批时查），放策略会造成重复；这正是方案乙的主要代价。
- 代价（如实报告）：策略变薄，可能被质疑“只是状态选择器”；Service 里存在“返回 APPROVED 才检查名额”的流程假设。若第三种规则改变名额时机（候补、抽签、分时段），Service 需要改，不能只加一个策略文件。该风险已在第 8 节列出。

### 3.5 与方案乙的对照（详见 05-类图方案对比.md）

| 维度 | 甲（采用） | 乙（未采用） |
|---|---|---|
| 名额逻辑 | CapacityChecker 一处 | 各策略一份 |
| 改名额口径 | 1 个文件 | 2–3 个文件（随规则增长） |
| 新规则 | 3 个文件起；特殊时机 5–6 | 3 个文件起；接口扩展 5–6 |
| 不超卖保证 | 集中、易证明 | 依赖每个策略自觉 |
| 策略接口 | 简单 | submit/approve 双阶段，偏重 |

选择甲的核心判断：本项目的规则差异集中在“审批方式”，名额是共性；把共性集中、差异下放，比让每条规则各自实现名额更符合当前需求。

### 3.6 扩展点

- 新增第三种规则且仍属“立即通过/待审核”两态：新增策略文件 + PolicyProvider 注册 + 测试，Service 不改。
- 新增规则需要新状态或新时机：先改状态枚举/Service 流程，再新增策略；预计 5–6 个文件，届时应重新评估甲是否仍合适。

## 4. 模式二：观察者 / 事件分发（3.3-C）

### 4.1 结构与协作

- Subject：RegistrationEventPublisher，维护 RegistrationObserver 列表。
- Observer：RegistrationObserver，方法 on_registration_event(event)。
- ConcreteObserver：MessageObserver，把事件写成 Message。
- 事件：RegistrationEvent，携带 registration_id、event_type、student_id、activity_id、result_status、occurred_at。
- 协作：Service 构造事件 → Publisher 分发给所有观察者 → MessageObserver 经 MessageRepository 写消息。Service 不知道“站内消息”这个具体渠道。

### 4.2 通知失败是否影响报名事务（Q-04）

采用**强一致**：报名/审批与消息写入在同一事务内。MessageObserver 经 MessageRepository 写消息失败会抛异常，异常穿过 Publisher 回到 Service，事务回滚，报名不生效并向用户提示；失败日志在事务外记录。这样不存在“报名成功但用户没收到通知”的静默状态，符合 B.2-6。

代价：通知与业务强耦合在事务上，无法异步削峰；这是本项目“通知是报名生效必要告知”的定位决定的，不是无意为之。

### 4.3 如何避免重复通知

1. 每次成功状态迁移只构造并发布 1 个事件；
2. Message 使用 (registration_id, event_type) 唯一键，MessageObserver 重复收到同一事件时跳过；
3. 审批用条件更新（Q-05），并发重复批准只会成功一次；
4. 同一学生同一活动只允许一条有效报名（唯一约束），重复提交不会产生第二个报名/事件；
5. 通知失败整体回滚、不重试，因此不会因重试产生重复消息。

### 4.4 代价

- 增加 Publisher/Observer/Event 三个概念，阅读成本上升；
- 事务内回调，异常传播链更长，调试要追 Publisher → Observer；
- 若未来要异步通知，需要把事务边界改成“报名提交 + outbox/事件表”，那是 CR 级别改动。

### 4.5 扩展第二通知渠道

新增一个 RegistrationObserver 实现（如 EmailObserver）并注册到 Publisher，Service 与现有 MessageObserver 均不改；预计 2–3 个文件。这正是观察者模式在本项目的收益点。

## 5. SOLID 落点

| 原则 | 落点 | 证据 | 代价/注意 |
|---|---|---|---|
| SRP | 实体/仓储/服务/策略/容量/事件/通知各司其职；RegistrationService 只编排报名链路，活动/消息由 ActivityService/MessageService 承接 | 类图 v1.2、类模型 §1 | 类数量增加，需避免过度拆分 |
| OCP | 新规则加策略+注册；新渠道加观察者 | 类模型 §3.6、§4.5 | 新流程/新状态仍要改 Service，不是完全开放 |
| LSP | 两策略都可替换 RegistrationPolicy，只返回 RegistrationStatus | 类图实现关系、时序图 | 返回值语义不同，调用方必须按状态分支 |
| ISP | 四个仓储接口分开；Observer 只有一个方法 | 类图 v1.2 | 接口多，样板代码增加 |
| DIP | Service 依赖 PolicyProvider/Repository/Policy 抽象；CapacityChecker、Publisher 作为领域/基础设施具体类由组合根注入（类模型 §3 已写明例外） | 类图依赖箭头、类模型 §3 | 需要依赖注入/组装点，测试要搭假实现 |

## 6. 其他关键设计决策摘要（Q-01～Q-10）

| 决策 | 选择 | 对设计的影响 |
|---|---|---|
| Q-01 基本条件 | 未开始 + 无重复 + 有名额 + 未删除/取消 | Service 公共校验；Activity.deleted_at |

## 7. 可测试性与可维护性

- 策略测试：给定 Activity，断言 decide 返回 APPROVED/PENDING，不需要数据库。
- CapacityChecker 测试：用假 RegistrationRepository 返回 count，覆盖 count < capacity、=、>。
- Service 测试：注入假策略/假仓储/假 Publisher，验证“PENDING 不查名额”“APPROVED 查名额”“通知失败回滚”。
- 观察者测试：MessageObserver 用假事件 + 假 MessageRepository 验证写消息；Publisher 验证多观察者分发。
- 变更度量（3.7）：后续 CR 按新增类数、修改核心类数、回归失败数、AI 轮次、修改时长统计，用客观数据评价甲/乙的取舍。

## 8. 已知不足与风险（如实报告）

1. **策略偏薄**：策略只返回状态，可能被认为“策略模式用得不够充分”；理由是名额是公共不变量。若评审认为策略应承担更多规则，可讨论把“是否立即占名额”也放到策略接口，但那会削弱甲的集中优势。
2. **Service 流程假设**：APPROVED → 查名额；第三种规则若改变时机（候补/抽签），Service 需要改，OCP 在流程层不完整。
3. **CapacityChecker 热点**：所有提交/审批依赖它，未来若把多种配额规则塞入会膨胀；应限制其职责为“容量口径与校验”。
4. **save 双语义**：创建与条件更新都走 save，实现时容易混淆；若复杂度上升，拆 confirm_approval 并升类图 v1.2。
5. **观察者与事务耦合**：调试链路长，异步化需要改事务模型；当前为满足 Q-04 有意为之。
6. **Repository 接口数量**：三个接口 + SQLite 实现增加样板代码，换取可测试性与 DIP。
