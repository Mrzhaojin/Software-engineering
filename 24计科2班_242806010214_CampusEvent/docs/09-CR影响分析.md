## 1. 变更摘要

| 编号 | 变更 | 关键要求 |
|---|---|---|
| CR-01 | 新增“年级限定直接报名” | Student 新增 grade（1–4）；仅 grade∈{2,3} 可报名；其他年级明确提示；仍遵守名额、开始时间、重复报名公共约束；原直接/审核行为不变 |
| CR-02 | 新增模拟邮件通知 | 报名通过、审核通过/拒绝时，站内消息与模拟邮件同时记录；邮件失败要记录错误但不得回滚已成功报名；同一业务事件不重复发送；不把邮件代码写进 RegistrationService |

## 2. CR-01 影响分析

### 2.1 受影响对象

| 对象 | 变化 | 说明 |
|---|---|---|
| Student | 新增 grade: int（1–4） | 需要数据迁移与演示账号补 grade；S004（大四）用于 CR1-04 |
| Activity | 新增 grade_limited: bool（或新 policy_type） | 表示“年级限定直接报名”；仅对直接报名型生效 |
| PolicyProvider / PolicyRegistry | 选择逻辑扩展 | 根据 activity 的 policy_type + grade_limited 选择策略；接口可能从 get(policy_type) 调整为 get(activity) |
| RegistrationPolicy | 新增实现 | GradeLimitedDirectPolicy 复用 DirectRegistrationPolicy，先检查 grade，再返回 APPROVED |
| PolicyRejectedError | 新增异常 | grade 不符时抛出，带明确原因；现有路由已捕获 DomainError，可显示提示 |
| RegistrationService | 尽量不改；若采用可组合方案只改“取策略”一行 | 公共校验、名额检查、事件发布流程不变 |
| ActivityService / 表单 / 列表 / 详情 | 增加“年级限定”选项与显示 | 变更的是输入与展示，不是核心报名流程 |
| schema / 迁移 | students 加 grade；activities 加 grade_limited | 建议 ALTER TABLE；避免重建 activities 表（见 2.2） |
| 演示账号 / README | 增加 S004，补 S001–S003 的 grade | 用于 CR1-01～04 和大一/大四拒绝验证 |
| 测试 | 新增 CR1-01～CR1-05 | 另加 grade 缺失/非法值、原有策略回归 |

### 2.2 两种设计及取舍

**方案 A：新增 policy_type = grade_direct（独立策略）**
- 新增 GradeLimitedDirectPolicy；PolicyRegistry 注册 grade_direct；RegistrationService 零修改。
- 缺点：activities 表的 CHECK 约束需要重建表才能接受新枚举值；对已部署的 SQLite 有迁移风险，需关闭外键、建新表、复制、改名、恢复，步骤较多。

**方案 B：活动加 grade_limited 布尔字段 + 策略装饰器（推荐）**
- Activity 仍用 policy_type=direct/audit；direct + grade_limited=1 时，Provider 返回 GradeLimitedDirectPolicy（内部组合 DirectRegistrationPolicy，先查 grade 再委托）。
- RegistrationService 只把 provider.get(policy_type) 调整为 provider.get(activity) 一行；核心流程不变。
- 数据库只需 ALTER TABLE ADD COLUMN，避免重建 activities；迁移风险低。
- 仍保持策略可替换、可组合；原 direct/audit 在 grade_limited=0 时行为完全不变。
- 代价：Activity 多一个标志位，Provider 接口签名变化；需要在 ActivityService 校验“grade_limited 只能配合 direct”。

**推荐 B**：它更符合 CR 的“可组合规则”提示，且不冒险重建已部署的数据表；RegistrationService 只动一行，能作为“设计模式降低了变更成本”的证据。

### 2.3 预计修改范围

- 新增类/接口：GradeLimitedDirectPolicy、PolicyRejectedError（2 个）。
- 修改：Student/Activity（字段）、PolicyProvider/Registry、RegistrationService（1 行）、ActivityService（校验）、routes/templates、seed/login/README、schema/迁移。
- 新增测试：CR1-01～CR1-05，加 grade 边界；回归 C1–C10。
- 估约：8–10 个文件修改，2 个新类，1 个迁移脚本。

## 3. CR-02 影响分析

### 3.1 受影响对象

| 对象 | 变化 | 说明 |
|---|---|---|
| EmailLog（实体/表） | 新增 | 字段：log_id、registration_id、event_type、recipient、subject、content、status、error、created_at、event_key（唯一） |
| EmailLogRepository | 新增 | save、find_by_event_key、list（可选） |
| MockEmailSender | 新增 | 模拟发送，记录收件人/主题/内容/状态/时间；支持模拟失败 |
| EmailObserver | 新增 | 实现 RegistrationObserver；只处理通过/拒绝事件；失败捕获并记录，不向上抛 |
| RegistrationEventPublisher | 组装扩展 | 观察者列表增加 EmailObserver；不改变发布语义 |
| RegistrationService | **不修改** | 邮件代码不进 Service；站内通知仍由 MessageObserver 负责 |
| MessageObserver / Q-04 | 不变 | 站内消息仍在事务内；失败仍回滚，保持强一致 |
| 配置/路由 | 小幅 | 观察者注册、模拟失败开关；可选邮件日志查询页（非必需） |
| 测试 | 新增 CR2-01～CR2-05 | 失败不滚回、失败日志、重复发送防护、原 C1–C10 回归 |

### 3.2 事务语义设计（关键）

- 站内消息：MessageObserver 保持原样，在 Service 事务内；失败抛异常 → 回滚（Q-04 不变）。
- 模拟邮件：EmailObserver 放在观察者列表最后，内部 try/except；发送失败写 EmailLog(status=FAILED, error=...)，不抛异常 → 报名事务正常提交（CR2-03）。
- 观察者顺序：MessageObserver 先、EmailObserver 后。若站内通知失败，邮件不会执行，报名回滚，避免“报名没成但邮件已发”。
- 残余风险：邮件在提交前执行，极端情况下提交本身失败会出现“邮件已发但报名回滚”。课程 mock 可接受；若要求严格，可改为 after-commit 分发，但会改 Service/Publisher 事务边界，超出本次最小改动。
- 去重：EmailLog.event_key 唯一（如 APPROVAL_APPROVED:registration_id）；EmailObserver 发送前查重，保证 CR2-04 不重复。

### 3.3 收件人

- 不新增 Student.email 字段，使用演示邮箱 student_id@campus.demo；邮件日志记录该 recipient。CR 只要求“记录收件人”，mock 环境够用；若老师要求真实邮箱字段，可再迁移。

## 4. 公共约束与回归

- CR-01 的年级限定活动仍走 RegistrationService 的公共校验：开始时间、重复报名、名额检查（APPROVED 分支）全部不变。
- CR-02 不改变报名/审批状态机；只新增通知渠道。
- 回归：C1–C10 全跑；另加 CR1-01～05、CR2-01～05；原有直接/审核测试保持。
- 部署：迁移脚本先在本地 baseline 数据库副本上测试；上线前备份 campusevent.db。

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| SQLite 迁移 | 已部署数据损坏 | 采用方案 B 只 ADD COLUMN；迁移前备份；用 baseline 数据库副本测试 |
| grade 数据缺失 | 年级限定误判 | 迁移默认值 + 更新 S001–S004；启动时校验 |
| 邮件失败拖垮报名 | 违反 CR2-03 | EmailObserver 内部捕获并记录，绝不向上抛 |
| 邮件重复 | 违反 CR2-04 | EmailLog.event_key 唯一 + 发送前查重 |
| 观察者顺序 | 站内失败后邮件已发 | 固定 MessageObserver 在前、EmailObserver 在后 |
| 设计漂移 | 报告与代码不一致 | 类图/类模型/时序图升 v2.0；AI_DEV_LOG 记录 |

## 6. 结论

- 已确认 CR-01 方案 B（可组合装饰器 + grade_limited 标志），RegistrationService 核心流程只改一行；不重建 activities 表。
- 已确认 CR-02 方案 A（EmailObserver + MockEmailSender + EmailLog），Service 不改；邮件失败捕获并记录，站内消息仍保持 Q-04 强一致。
- 实际新增 2 个策略/异常类 + 4 个邮件相关类（EmailLog、EmailLogRepository、MockEmailSender、EmailObserver），修改约 10 个文件；新增 9 条 CR 测试 + 1 条迁移测试，31 tests 通过。
