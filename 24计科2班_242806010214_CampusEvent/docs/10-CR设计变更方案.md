# 实验二 CR 设计变更方案（v2.0 草案）

> 基线：baseline-v1（8accd33）｜ 分支：change-v2 ｜ 日期：2026-11-26
> 本方案对应 CR-01 / CR-02；学生已确认采用 CR-01 方案 B、CR-02 方案 A；已完成 v2.0 图与实现，待 CR 验收。未推送 GitHub。

## 1. 设计原则

- 核心流程不变：RegistrationService 的提交/审批/取消编排不重写；CR-01 只改“取策略”一行，CR-02 不改 Service。
- 公共约束集中：开始时间、重复报名、名额检查仍在原位置；年级检查放新策略，不复制公共规则。
- 通知分渠道治理：站内消息保持事务内强一致；邮件失败只记录，不回滚。
- 版本可追溯：CR 前 v1.x，CR 后 v2.x；完成回归后打 change-v2。

## 2. CR-01 设计（推荐方案 B）

### 2.1 新增/修改

| 类/接口 | 类型 | 职责 |
|---|---|---|
| Student.grade | 字段 | 1–4 年级；演示账号 S001=2、S002=1、S003=3、S004=4 |
| Activity.grade_limited | 字段 | 是否年级限定直接报名；仅允许与 policy_type=direct 组合 |
| GradeLimitedDirectPolicy | 策略 | 先检查 student.grade 是否 2/3；不符合抛 PolicyRejectedError；符合则委托 DirectRegistrationPolicy |
| PolicyRejectedError | 异常 | 带明确中文原因，路由捕获后 flash |
| PolicyProvider/PolicyRegistry | 接口/实现 | get(activity)：direct + grade_limited 返回年级策略，其余按 policy_type 返回原策略 |
| RegistrationService | 服务 | 仅把 get(policy_type) 改为 get(activity)；其余流程不变 |
| ActivityService | 服务 | 校验 grade_limited 只能用于 direct；表单/列表/详情展示 |
| schema/迁移 | 数据 | students ADD grade；activities ADD grade_limited；插入 S004；PRAGMA user_version=2 |

### 2.2 提交流程（年级限定）

1. Service 公共校验：学生存在、活动未开始/未删除、无重复有效报名。
2. Provider 返回 GradeLimitedDirectPolicy。
3. policy.decide(activity, student)：
   - grade 不是 2/3 → 抛 PolicyRejectedError（提示“仅限大二、大三学生报名”），事务回滚，不建报名。
   - grade 是 2/3 → 返回 APPROVED。
4. Service 对 APPROVED 执行 CapacityChecker.ensure_available；名额不足仍失败。
5. 创建 Registration，发布 SIGNUP_APPROVED 事件；站内消息 + 邮件。

### 2.3 兼容性

- grade_limited=0 时，Provider 返回原 DirectRegistrationPolicy/AuditRegistrationPolicy，行为完全不变。
- 原有 C1–C10 不应受影响；新增 S004 账号供 CR1-04 使用。

## 3. CR-02 设计（推荐方案 A：观察者捕获）

### 3.1 新增/修改

| 类/接口 | 类型 | 职责 |
|---|---|---|
| EmailLog | 实体/表 | 记录 log_id、registration_id、event_type、recipient、subject、content、status、error、created_at、event_key（唯一） |
| EmailLogRepository | 仓储 | save、find_by_event_key、list（可选） |
| MockEmailSender | 发送器 | 模拟发送；成功/失败均写日志；无真实网络 |
| EmailObserver | 观察者 | 实现 on_registration_event；只处理 APPROVED/REJECTED 事件；异常捕获并记录，不抛出 |
| RegistrationEventPublisher | 发布者 | 观察者注册：MessageObserver 先，EmailObserver 后 |
| RegistrationService | 服务 | 不修改 |

### 3.2 通知语义

| 渠道 | 事务 | 失败行为 |
|---|---|---|
| 站内消息 MessageObserver | 在 Service 事务内 | 抛异常 → 整体回滚（Q-04 不变） |
| 模拟邮件 EmailObserver | 在发布循环内执行，但内部捕获异常 | 写 EmailLog（FAILED，错误信息），不抛 → 报名提交成功（CR2-03） |

- 去重：EmailLog.event_key 唯一；发送前查重；同一事件不会重复邮件。
- 事件范围：SIGNUP_APPROVED、APPROVAL_APPROVED、APPROVAL_REJECTED；SIGNUP_PENDING 不发邮件（CR 要求通过/拒绝结果）。
- 收件人：student_id@campus.demo（mock 演示邮箱）。

### 3.3 残余风险

邮件在报名事务提交前尝试发送；极端情况下（邮件已发、随后提交失败）会出现通知与数据不一致。课程 mock 场景可接受；若老师要求严格，可后续升级为 after-commit 分发。

## 4. 数据库迁移

- students：ALTER TABLE students ADD COLUMN grade INTEGER NOT NULL DEFAULT 1；更新 S001–S003，插入 S004。
- activities：ALTER TABLE activities ADD COLUMN grade_limited INTEGER NOT NULL DEFAULT 0；不改 policy_type CHECK，不重建表。
- email_logs：新建表 + event_key 唯一索引。
- 迁移脚本幂等：用 PRAGMA table_info 判断列是否存在；user_version=2；迁移前备份。
- 在 baseline-v1 数据库副本上测试迁移，再对部署数据库执行。
