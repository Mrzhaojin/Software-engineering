## UC-01 管理活动

- **编号/名称**：UC-01 管理活动
- **参与者**：Admin
- **目标**：创建、编辑或软删除一个活动。
- **触发器**：管理员在活动管理页选择“新建 / 编辑 / 删除”。
- **前置条件**：管理员使用固定演示账号进入管理端。
- **后置条件**：
  - 成功：活动新增或修改落库；删除采用软删除（活动对用户隐藏，报名与消息保留）。
  - 失败：数据不变，界面给出错误提示。
- **基本事件流**：
  1. 管理员进入活动管理页，系统展示活动列表（名称、类型、时间、地点、容量、报名方式、状态）。
  2. 管理员选择新建、编辑或删除。
  3. 系统显示表单（新建/编辑）或删除确认框。
  4. 管理员填写或修改：名称、类型、时间、地点、人数上限、报名方式。
  5. 系统校验必填项、容量为正整数、时间格式合法。
  6. 系统保存变更，活动信息持久化。
  7. 系统刷新列表并提示操作成功。
- **扩展事件流**：
  - A-1 校验失败：提示具体字段错误，保留已填内容，不保存。
  - A-2 删除已有报名的活动：按 Q-06 执行软删除，提示“活动已下线”，报名与消息保留。
  - A-3 活动不存在或已被删除：提示并刷新列表。
- **业务规则**：B.2-7；Q-06（软删除）。
- **数据需求**：Activity 全部字段；capacity 正整数。
- **关联需求/验收**：REQ-19、REQ-20；C1。

## UC-02 浏览活动

- **编号/名称**：UC-02 浏览活动
- **参与者**：Student、Admin（共享用例）
- **目标**：查看活动列表与详情，判断是否可报名以及剩余名额。
- **触发器**：用户进入活动列表，或从消息、统计页面跳转到活动详情。
- **前置条件**：无（演示账号可直接进入）。
- **后置条件**：成功展示列表/详情；无数据时显示空状态提示。
- **基本事件流**：
  1. 用户进入活动列表。
  2. 系统展示活动名称、类型、时间、地点、报名方式与剩余名额（capacity − 已通过数）。
  3. 用户可按名称筛选。
  4. 用户选择活动，系统展示详情（含剩余名额、报名方式、活动状态）。
  5. 用户返回列表。
- **扩展事件流**：
  - A-1 筛选无结果：提示“无匹配活动”。
  - A-2 活动已软删除：列表不显示；直接访问详情提示活动不存在。
  - A-3 余量发生变化：以服务端最新数据为准，页面刷新后更新。
- **业务规则**：B.2-3（名额口径）；Q-10（余量展示）。
- **数据需求**：Activity 字段；剩余名额 = capacity − 已通过报名数。
- **关联需求/验收**：REQ-21、REQ-23；C4 辅助观察。

## UC-03 报名活动

- **编号/名称**：UC-03 报名活动
- **参与者**：Student
- **目标**：完成一次报名：直接报名型立即通过，审核型进入待审核。
- **触发器**：学生在活动详情点击“报名”。
- **前置条件**：使用固定演示账号；活动存在且未开始；该学生对该活动无“待审核/已通过”的有效报名。
- **后置条件**：
  - 成功：新增报名记录（已通过或待审核），同一事务写入站内消息。
  - 失败：不产生报名记录，提示失败原因。
- **基本事件流**：
  1. 学生打开活动详情，点击“报名”。
  2. 系统校验：活动存在且未开始、未被软删除、无重复有效报名（Q-01）。
  3. 系统读取活动报名方式 policy_type：
     - 3a 直接报名型：检查剩余名额（Q-07 服务前置检查 + 策略兜底）；名额充足时创建“已通过”报名，并写站内消息（同一事务，Q-04）。
     - 3b 审核型：创建“待审核”报名，并写站内消息；当前满员也允许提交（Q-02）。
  4. 系统返回活动详情或“我的报名”，显示最新状态。
  5. 系统提示报名结果（报名成功 / 已提交待审核）。
- **扩展事件流**：
  - A-1 活动已开始：拒绝报名（B.2-5、REQ-16）。
  - A-2 已存在有效报名：拒绝重复报名（B.2-4、REQ-13）。
  - A-3 直接报名型名额不足：拒绝，提示名额已满（B.2-1、REQ-06）。
  - A-4 并发导致名额被占：条件更新失败，回滚并提示重试（Q-05）。
  - A-5 通知写入失败：整体事务回滚，提示报名未成功，并在事务外记录失败日志（Q-04、REQ-17）。
  - A-6 活动已软删除：提示活动不存在。
- **业务规则**：B.2-1、B.2-2、B.2-3、B.2-4、B.2-5、B.2-6；Q-01～Q-05、Q-07。
- **数据需求**：Registration、Message；报名初始状态由 policy_type 决定。
- **关联需求/验收**：REQ-06、07、08、11、13、16、17；C2、C3、C4、C5。

## UC-04 审批报名

- **编号/名称**：UC-04 审批报名
- **参与者**：Admin
- **目标**：对待审核报名做出批准或拒绝决定。
- **触发器**：管理员打开待审核列表并选择一条报名。
- **前置条件**：存在“待审核”报名；管理员使用固定演示账号进入审批页。
- **后置条件**：
  - 成功：报名状态变为“已通过”或“已拒绝”，同一事务写入站内消息。
  - 失败：状态不变，提示失败原因。
- **基本事件流**：
  1. 系统展示待审核报名（学生、活动、申请时间）及活动当前余量。
  2. 管理员选择批准或拒绝。
  3. 批准时系统再次检查剩余名额（Q-07）。
  4. 系统更新报名状态：批准→已通过；拒绝→已拒绝。
  5. 同一事务写入站内消息（Q-04）。
  6. 系统提示处理结果并刷新列表。
- **扩展事件流**：
  - A-1 批准时余量已满：批准失败，不超出容量（B.2-3、C8）。
  - A-2 并发审批同一报名：条件更新或唯一约束失败，提示“该报名已被处理”（Q-05）。
  - A-3 通知写入失败：整体回滚，提示处理未成功，并在事务外记录失败日志（Q-04、REQ-17）。
  - A-4 报名已非待审核：拒绝操作并刷新。
- **业务规则**：B.2-2、B.2-3、B.2-4、B.2-6；Q-04、Q-05、Q-07。
- **数据需求**：Registration.status、Message。
- **关联需求/验收**：REQ-09、10、12；C6、C7、C8。

## UC-05 取消报名

- **编号/名称**：UC-05 取消报名
- **参与者**：Student
- **目标**：取消自己的“待审核/已通过”报名。
- **触发器**：学生在“我的报名”选择一条报名并点击取消。
- **前置条件**：存在属于本人的“待审核/已通过”报名。
- **后置条件**：
  - 成功：报名状态变为“已取消”，记录保留，统计同步更新。
  - 失败：状态不变，提示原因。
- **基本事件流**：
  1. 系统展示本人“待审核/已通过”报名。
  2. 学生选择一条并确认取消。
  3. 系统判断活动是否已开始：
     - 3a 活动未开始：允许取消，状态改为“已取消”。
     - 3b 活动已开始且报名为“待审核”：允许取消（Q-03）。
  4. 系统保留历史记录，剩余名额统计同步，提示取消成功。
- **扩展事件流**：
  - A-1 活动已开始且报名为“已通过”：拒绝取消（Q-03）。
  - A-2 报名已取消或已拒绝：提示不可重复取消。
  - A-3 报名不属于当前学生：拒绝操作。
- **业务规则**：B.2-5；Q-03。
- **数据需求**：Registration.status、updated_at。
- **关联需求/验收**：REQ-14、REQ-15；C9。

## UC-06 查看站内消息

- **编号/名称**：UC-06 查看站内消息
- **参与者**：Student
- **目标**：查看报名与审批结果消息，并标记已读。
- **触发器**：学生进入站内消息页面。
- **前置条件**：使用固定演示账号。
- **后置条件**：消息列表展示；被选中的消息标记为已读。
- **基本事件流**：
  1. 系统按时间倒序展示消息（内容、关联活动、时间、已读状态）。
  2. 学生选择一条消息，系统显示内容并将 is_read 置为已读。
  3. 返回列表，未读数量更新。
- **扩展事件流**：
  - A-1 无消息：显示空状态提示。
  - A-2 关联活动已软删除：只显示消息文本，不跳转活动详情。
- **业务规则**：B.1 Message。
- **数据需求**：Message 全部字段。
- **关联需求/验收**：REQ-05、07、10；C6、C7（通知证据）。

## UC-07 查看活动统计

- **编号/名称**：UC-07 查看活动统计
- **参与者**：Admin
- **目标**：查看单个活动的已通过数、待审核数与剩余名额。
- **触发器**：管理员进入统计页并选择活动。
- **前置条件**：管理员使用固定演示账号；活动存在。
- **后置条件**：展示该活动的统计结果。
- **基本事件流**：
  1. 系统展示活动选择器。
  2. 管理员选择活动。
  3. 系统统计：已通过数、待审核数、剩余名额（capacity − 已通过数）。
  4. 系统展示统计结果。
- **扩展事件流**：
  - A-1 无活动：提示无数据。
  - A-2 活动已软删除：不在可选列表，或标注“已下线”。
- **业务规则**：B.2-3。
- **数据需求**：Registration.status 聚合；Activity.capacity。
- **关联需求/验收**：REQ-11、REQ-22；C9（统计同步）。

## 9. 补充约束（全局）

- 界面文字为中文；错误输入给出可理解提示，不导致应用崩溃。
- 所有活动、报名、消息数据持久化；服务重启后保持一致（REQ-18）。
- 报名与审批的写操作使用数据库事务；容量校验与状态更新保证原子性（Q-05）。
- 站内消息失败不得产生“已报名但无告知”的静默状态（Q-04）。
- 软删除活动不得从历史报名与消息中抹除关联数据（Q-06）。
